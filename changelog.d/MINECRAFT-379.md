### Added
- Pathfinder region/circuit core (`pathfinder` package): deterministic 512x512-block region identity, Chebyshev ring enumeration, and a spatially-coherent circuit ordering, producing the designed 8/16/24/32-region circuits for levels 2-5 and an 8-checkpoint local loop for level 1 (settled 2026-10-18). A route is a pure function of origin region + level, so it is identical across villagers, retries, reload and multiplayer sessions.
- `PathfinderCheckpoint`/`PathfinderPosition`: each checkpoint is a concrete, dimension-aware position; the reach radius to check against is a parameter at check time, not stored on the checkpoint, so a config change takes effect immediately for every in-progress and already-cached route.
- `PathfinderTerrainPlacer`: real, read-only terrain-safe checkpoint placement - a small bounded, deterministic search for a column with no lava underfoot, standable footing, two blocks of headroom, and valid world-height bounds. Fails closed (returns no checkpoint) rather than falling back to an unsafe candidate when every searched offset fails; `PathfinderRouteGenerator`/`PathfinderRouteStorage` propagate that as a failed, uncached route generation, and `PathfinderAttempts` reports it to the player as a retryable "no safe route" message instead of starting an invalid attempt. Never modifies terrain. Successful routes are cached server-wide per (dimension, origin, level) by `PathfinderRouteStorage` so checkpoint coordinates stay fixed across retries/reloads/later infrastructure edits.
- `PathfinderProgress`: server-authoritative, in-order checkpoint validation (dimension + proximity, not region entry) with out-of-order rejection, an overall completion time limit evaluated atomically with every reach report, and a closing leg back to the first checkpoint.
- A working vertical slice: right-click a Pathfinder villager (profession + "Route Board" workstation block/POI, reusing the shared `VillagerJobSites` helper) to start an attempt at its current unlocked maximum level, or run `/pathfinder start <level>` to select any already-unlocked earlier circuit instead (server-validated; a locked level is rejected). A coarse server tick evaluates each online, alive player's active attempt and advances it on real movement. Completion/expiry/death clear the attempt only once a real save of it has been read back off disk and confirmed absent there (not merely queued or "the async task finished" - NeoForge's own `SavedData` swallows a failed write's `IOException` inside that task, so joining it alone cannot tell success from silent failure); if that confirmation fails, the attempt is retried on the next tick rather than lost, and the reward is withheld until it's actually confirmed durable - verified with a real, injected OS-level write failure (a read-only save directory), not just a serialization round trip. Death (the real `LivingDeathEvent`, not deferred to respawn) fails the attempt outright; `onServerTick` also skips evaluating any player who isn't alive, as defense in depth. A minimal HUD overlay shows next-checkpoint direction and remaining time (or cross-dimension guidance instead of a meaningless arrow when the player isn't in the checkpoint's own dimension), mirroring the Dispatcher's own HUD pattern.
- `PathfinderVillagerLevel`/`PathfinderVillagerProgress`/`PathfinderVillagerProgressStorage`: a Pathfinder villager's own level, tracked server-wide by villager UUID (independent of whether that villager's entity is currently loaded - a circuit routinely completes regions away from its own villager), advances only via actual circuit completions AT the villager's current level (3 by default) - a completion for a level the villager has already moved past is credited its reward but does not advance progression further, closing a concurrency exploit where many concurrent low-level attempts finishing in sequence could otherwise unlock far higher levels than any of them actually ran. Deliberately NOT `VillagerData`'s trade-based level either, which `setProfession` preserves across a profession change and would otherwise let a villager trade-leveled under any other profession instantly unlock high Pathfinder levels.
- `PathfinderServerConfig`: timer, reward, reach-radius and level-advancement-threshold values are now a real `ModConfigSpec` (following `DispatcherOfferConfig`'s pattern), not plain constants. The timer is genuinely snapshotted into an attempt's own record at start time; reach radius, reward and the level threshold are read fresh at the moment they're used, so a config change takes effect immediately rather than being frozen at whatever it was when a route/attempt first came into existence.
- Block/profession textures are an explicit placeholder (the Dispatcher's own board/profession art, reused) pending real art.
- Review follow-up (round 6): the reward-payout durability check now also confirms the villager progression credit landed on disk, not just the attempt-clear - `PathfinderVillagerProgressStorage` is a separate `SavedData` file from the attempt's own, so one write could previously succeed while the other silently failed, paying the reward while the earned progression was lost. A completion's record now carries a `died` flag: a death-clear that cannot be confirmed durable leaves the record marked `died` (not its original live shape, and not discarded), so a later tick - even one landing after respawn - recognizes it as terminal instead of advancing or completing it off subsequent movement. Covered by new fault-injection `GameTest`s for a progression-only write failure and for death-during-write-failure surviving respawn and closing-checkpoint movement, both using real injected OS-level write failures. (Also fixed along the way: `SavedData#save` silently clears a `SavedData`'s dirty flag even on a FAILED write, so the villager-progression write must be explicitly re-marked dirty on every payout retry attempt, not just once - otherwise a failed progression write would never actually retry.)
- Review follow-up (round 7): round 6's dual-verification still clear/marked-credited the attempt optimistically before the progression write was independently confirmed durable - a save landing the attempt-clear while the progression write failed could delete the completed run from disk with only an in-memory restoration backing it up (a crash/restart right then loses the whole run), and even without a crash, a later unrelated autosave of that in-memory-restored record could persist `progressionCredited=true` while the progression file stayed stale, permanently settling the attempt as "credited" with the credit itself never landing. The payout is now a strict two-phase sequence: progression is credited and confirmed durable FIRST, with the attempt record itself untouched throughout that phase (so any crash/retry there just resumes from whatever was last durably saved); only once progression is confirmed does phase two clear the attempt. Closing a narrower residual gap purely in-process (a crash between progression landing durably and the attempt's own `progressionCredited` flag catching up), each real completion now carries a stable, persisted per-attempt identity so a second credit attempt for the exact same completion after a restart is a safe no-op rather than a double count. The progression-only fault-injection `GameTest` now also reloads the attempt file straight back off disk (bypassing the live singleton) mid-failure to directly prove a restart at that exact moment would not lose the run.
- Review follow-up (round 8): round 7's idempotency guard tracked only the single MOST RECENTLY credited attempt key per villager, which suppressed a repeat for the same attempt (A, A) but not an interleaving of two different players' pending completions on the same villager (A, B, A) - crediting B overwrote A's remembered key, so A's own still-legitimately-pending retry (its own verification never confirmed) no longer matched anything and was credited a second time, advancing progression from two real completions to three. `PathfinderVillagerProgressStorage` now tracks every still-retryable credited attempt key per villager in a set, not just the last one, forgetting one only once its attempt is fully, durably settled (reward granted, attempt cleared for good) so the set stays bounded to attempts still actually pending. Covered by a new `GameTest` with two distinct players finishing against the same villager while the progression write fails, confirming both are credited exactly once each (never three times) and the villager does not falsely unlock the next level.
- Post-merge follow-up (round 9): `IOUtilities#waitUntilIOWorkerComplete` can itself throw - a failed write's own asynchronous temp-file cleanup can race the write's target path changing underneath it and surface an unchecked `CompletionException`/`UncheckedIOException`, not the plain `IOException` a failed write alone produces. That call used to sit outside `PathfinderTickHandler`'s durability-check try blocks entirely, so it escaped `evaluate`, then `onServerTick`, then NeoForge's own event bus - crashing the GameTest server in CI instead of leaving the pending attempt safely retryable (never observed in gameplay, only in exactly this fault-injection path, but a real production-path robustness gap regardless). The whole save-then-verify sequence is now one try block in both durability checks, catching `RuntimeException` alongside `IOException`: the entire contract of those methods is "durably confirmed or not," so any failure reaching them must mean "not yet confirmed, retry later," never an uncaught crash. The fault-injection `GameTest`s also now drain the IO worker before removing their own fault directory, avoiding manufacturing this exact race from the test side at all.
